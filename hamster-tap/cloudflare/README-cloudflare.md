# Hamster Tap на Cloudflare Workers (бесплатный вариант)

Эта версия работает **без своего сервера и без вашего компьютера**: мини-апп и API крутятся
на edge Cloudflare, база — D1 (SQLite в облаке), бот получает сообщения через webhook.
Аренда домена не нужна: Worker получает постоянный `https://<имя>.<аккаунт>.workers.dev`.

```
Telegram-клиент ──HTTPS──► https://hamster-tap.<аккаунт>.workers.dev/
                            ├── /                  статика из web/ (Static Assets)
                            ├── /api/*             Worker → D1
                            └── /webhook/<secret>  Telegram → Worker (webhook-бот)
```

Локальная версия на Node.js (`server.js`) остаётся рабочей: они независимы и используют
разные базы (`data/app.db` и D1), общими остаются игровые правила (`lib/game.js`) и клиент (`web/`).
| Задания, достижения, косметика | `lib/quests.js`, `lib/achievements.js`, `lib/cosmetics.js` | общие каталоги для Node-версии и воркера (без импортов внутри) |
| Магазин и счета | `lib/shop.js`, `lib/invoice.js` | товары, payload счёта и `createInvoiceLink` (валюта XTR) |
| Код дня | `lib/dailycode.js` | генерация кода от даты (FNV-1a), нормализация ввода, клейм в `user_quests` |

## Что откуда берётся

| Что | Файл | Комментарий |
| --- | --- | --- |
| Правила баланса | `lib/game.js` | общий код с локальной версией, воркер импортирует его напрямую |
| Проверка `initData` | `lib/auth.js` | `node:crypto` в Workers поддерживается (compatibility date 2026-08-04) |
| API | `cloudflare/src/api.js` | те же маршруты и коды, что в Node-версии |
| Хранилище | `cloudflare/src/store.js` | D1-запросы + атомарные условные `UPDATE` |
| Игровые операции | `cloudflare/src/service.js` | асинхронная версия `lib/service.js` |
| Бот | `cloudflare/src/bot.js` | webhook, проверка `X-Telegram-Bot-Api-Secret-Token` |
| Напоминания | `cloudflare/src/push.js` | `scheduled()` по `[triggers]`; дедупликация через `push_log` |
| Платежи | таблица `payments` | `charge_id` уникален (`telegram_payment_charge_id` у звёзд, id платежа у ЮKassa), статус меняется условно `pending → succeeded` — повторный вебхук товар не выдаёт; возвраты звёзд — `tools/star-refund.js` |
| Каналы оплаты | `lib/payments/`, `lib/paylink.js` | внутри Telegram — звёзды, вне — рубли на внешней странице (ЮKassa); личные ссылки подписаны HMAC, ключи провайдера живут только на сервере |
| Схема БД | `cloudflare/schema.sql` | те же таблицы + `version` и `pending_card` |
| Новые колонки | `cloudflare/schema.sql` | описаны директивами `-- @add-column:`, инструмент добавляет их только там, где колонок ещё нет; разовые миграции данных — директивой `-- @on-add:` (выполняются лишь в тот запуск, когда колонка добавлялась) |

## Локальная разработка (без деплоя)

```powershell
cd C:\Users\user\hamster-tap
node tools/cf-d1-apply.js hamster-tap --local   # схема в локальной D1 (по утверждениям)
npx wrangler dev --port 8787                    # поднять воркер локально

# в другом окне:
node tools/cf-check.js                           # проверки API
$env:BASE_URL='http://localhost:8787'; node tools/browser-check.js   # проверки в браузере
```

Проверить, что таблицы на месте (без применения схемы):

```powershell
node tools/cf-d1-apply.js hamster-tap --local --check     # локальная база
node tools/cf-d1-apply.js hamster-tap --check            # удалённая база
```

`.dev.vars` (в `.gitignore`) задаёт локальные переменные, в том числе `ALLOW_DEV=1` —
благодаря этому вход без Telegram работает в тестах. В проде этот флаг выключен.

## Деплой

```powershell
# 1. один раз: вход в аккаунт Cloudflare (бесплатный, карта не нужна)
npx wrangler login

# 1а. подтвердите e-mail, если аккаунт новый (иначе Cloudflare вернёт code 10034)
#     письмо «Verify your email address» от Cloudflare, либо кнопка Resend на dash.cloudflare.com

# 2. деплой прода (создаст D1, применит схему, положит секреты, задеплоит, поставит webhook)
powershell -ExecutionPolicy Bypass -File .\tools\cf-deploy.ps1
```

Скрипт делает всё сам: проверяет (и при необходимости создаёт) workers.dev-поддомен аккаунта, создаёт базу `hamster-tap`, вписывает её `database_id` в `wrangler.toml`,
применяет `cloudflare/schema.sql` (через `tools/cf-d1-apply.js` — по утверждениям, с повторами),
сохраняет секреты `BOT_TOKEN` и `BOT_WEBHOOK_SECRET`,
деплоит воркер, узнаёт публичный адрес, прописывает его как `WEBAPP_URL`, деплоит повторно
и настраивает бота (`deleteWebhook` → `setWebhook` → команды → кнопка меню «🐹 Играть»).
В конце прогоняются проверки `tools/cf-check.js`. Скрипт можно запускать повторно: каждый шаг
идемпотентен, повторный запуск продолжит с места сбоя.

Тестовое окружение (своя D1 + `ALLOW_DEV=1`, webhook не перехватывается):

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\cf-deploy.ps1 -Target staging
```

Полезные команды:

```powershell
npx wrangler tail                       # живые логи воркера
npx wrangler d1 execute hamster-tap --remote --command "SELECT COUNT(*) FROM users"
npx wrangler d1 export hamster-tap --remote --output backup.sql   # бэкап базы
node tools/set-webhook.js --url https://<адрес> --secret <секрет> # переустановить webhook вручную
```

Напоминания по расписанию (`[triggers] crons` в `wrangler.toml`, раз в 20 минут):

```powershell
curl "http://127.0.0.1:8787/cdn-cgi/local/scheduled"   # прогнать рассылку локально (wrangler dev)
node tools/push-test.js 123456789 energy              # отправить себе такое же напоминание
node tools/star-sim.js                                 # проверить выдачу товара и запись чека
node tools/star-refund.js --list                       # покупки и чеки
node tools/star-refund.js <charge_id>                  # возврат звёзд покупателю
```

В проде расписание работает само: `wrangler deploy` ставит cron-триггеры из конфига.
Локально `wrangler dev` их не запускает — используйте адрес выше.

## Рублёвый канал оплаты (ЮKassa) в воркере

Внутри Telegram товары продаются только за звёзды; рубли идут на внешнюю страницу (свой
домен), которая обращается к воркеру по подписанному личному токену. Пока канал не нужен,
ничего делать не надо: `PAYMENTS_PROVIDER` по умолчанию `stars`, и мини-апп работает как прежде.

```powershell
# 1. Публичные переменные (wrangler.toml -> [vars] или wrangler secret для секретов)
#    PAYMENTS_PROVIDER=yookassa
#    PAY_PAGE_ORIGIN=https://pay.example.com      # CORS для страницы
#    PAY_PAGE_URL=https://pay.example.com/pay.html
#    YOOKASSA_SHOP_ID=<shopId>                    # публичный id магазина
#    YOOKASSA_RETURN_URL=https://pay.example.com/done.html
npx wrangler deploy

# 2. Секреты
npx wrangler secret put YOOKASSA_SECRET_KEY       # секретный ключ магазина
npx wrangler secret put YOOKASSA_WEBHOOK_SECRET   # часть адреса уведомлений
npx wrangler secret put PAY_LINK_SECRET           # подпись личных ссылок (пусто — BOT_TOKEN)

# 3. В кабинете ЮKassa: HTTP-уведомления на адрес
#    https://<адрес воркера>/api/payments/yookassa/<YOOKASSA_WEBHOOK_SECRET>
#    события: payment.succeeded, payment.canceled, refund.succeeded
#    Чеки (54-ФЗ): если включены «Чеки от ЮKassa» — поставьте YOOKASSA_RECEIPTS=1,
#    тогда в платёж добавляется receipt с VAT-кодом 1 и признаком «service».

# 4. Проверка: витрина отдаёт обе валюты, страница и уведомления защищены
node tools/cf-check.js https://hamster-tap.<аккаунт>.workers.dev
node tools/prod-check.js https://hamster-tap.<аккаунт>.workers.dev
```

Как устроена безопасность канала: токен ссылки — HMAC от `userId|exp` с коротким сроком
жизни; `payments.charge_id` уникален, а статус меняется условным
`UPDATE ... WHERE status = 'pending'`, поэтому повторный вебхук или сверка не выдадут товар
дважды; уведомление ЮKassa проверяется по секрету адреса и IP из официального списка
(подписи у него нет), после чего статус платежа всё равно перезапрашивается в API. Ответ
на уведомление всегда `200` — иначе сеть повторяет его сутки.

## Лимиты бесплатного тарифа (и почему клиент отправляет тапы пачками)

| Ресурс | Бесплатно | Наш расход |
| --- | --- | --- |
| Запросы Worker | 100 000 в сутки | одна пачка тапов раз в 1,5 с (или сразу при 10 нажатиях) + состояние раз в 60 с ≈ 800 запросов на активного игрока в сутки |
| Записи D1 | 100 000 строк в сутки | 1 запись на пачку тапов, поэтому ориентировочно **~100 активных игроков в сутки** |
| Чтения D1 | 5 млн строк в сутки | состояние игрока — единицы строк; рейтинг кэшируется на edge на 2 минуты |
| Хранилище D1 | 5 ГБ | ~1 МБ на 1000 игроков |
| Cron-запуски | входят в суточный лимит запросов Worker | раз в 20 минут = 72 запуска; каждый читает пачку кандидатов и пишет 1 строку на отправленное напоминание |

Если игроков станет больше — тариф Workers Paid ($5/мес) поднимает лимиты в разы
(10 млн запросов, 50 млн записей), код менять не нужно.

## Что стоит помнить

- **Webhook только один.** Для staging он не ставится, чтобы не забирать апдейты прода.
- **Правки в `web/`** подхватываются при следующем `wrangler deploy` (ассеты кэшируются на edge;
  при странностях — жёсткое обновление страницы).
- **Атомарность.** Списание монет и покупки идут через `UPDATE ... WHERE version = ? AND ...`,
  поэтому двойной клик по «Купить» не может списать дважды. Если процесс оборвался между
  двумя шагами покупки, она досчитывается при следующем обращении игрока (`pending_card`).
- **`ALLOW_DEV`** держите выключенным в проде: иначе любой сможет играть под чужим id.
- **Напоминания не спамят.** Каждое сообщение отправляется не чаще раза в сутки: слот занимает
  `push_log` (первичный ключ `user_id + kind + day`), поэтому лишние запуски крона ничего не дублируют.
  В сообщении есть кнопка «выключить напоминания» (нужен `allowed_updates` с `callback_query` — так ставит
  `tools/set-webhook.js`), а флаги лежат в `users.notify_energy / notify_daily / notify_rank`.
- **Оплата идемпотентна.** Товар выдаётся по ключу `payments.charge_id`
  (`telegram_payment_charge_id`): повторный `successful_payment` от Telegram ничего не дублирует.
  В `allowed_updates` webhook обязателен `pre_checkout_query` — без него Telegram не пришлёт
  подтверждение заказа (так ставит `tools/set-webhook.js`). По правилам Telegram у бота есть
  команда `/paysupport`, а возвраты оформляются инструментом на тот же чек.
- **Код дня** (`/code`) тоже считается на сервере: FNV-1a от даты, алфавит без
  похожих символов, а клейм хранится в `user_quests` (`daily_code`) — новых таблиц
  не потребовалось, повторный ввод за сутки отклоняется (409).
- **Миграции схемы безопасно повторять.** Новые колонки описаны директивами `-- @add-column:`:
  `node tools/cf-d1-apply.js hamster-tap` добавляет только отсутствующие, поэтому база с игроками
  обновляется без потери данных, а повторный запуск ничего не ломает. Разовая правка данных
  описывается директивой `-- @on-add: users.<колонка>: <SQL>`: она выполняется только в том
  запуске, когда колонка действительно добавлялась. Так переводились старые приглашения на
  правило «награда за 100 тапов друга»: у них `referral_paid` сразу помечается выплаченным,
  иначе вторая награда начислилась бы повторно.
- **Награда за друга платится за активность.** Другу приветственные 25 000 монет приходят
  на входе, а пригласившему 100 000 — когда друг сделает 100 тапов. Прогресс копится в
  `users.referral_taps` тем же `UPDATE`, что и тапы (лишних записей в D1 нет), а выплата
  защищена условным `UPDATE ... SET referral_paid = 1 WHERE referral_paid = 0 AND referral_taps >= ?`:
  флаг меняет ровно один запрос, поэтому параллельные пачки тапов не начислят бонус дважды.
- **Энергия за рекламу (Monetag + Chanify).** Сети перечислены в `AD_PROVIDERS` по
  приоритету, и первая доступная показывает рекламу:
  Monetag — rewarded-ролик внутри мини-аппа: сервер выдаёт одноразовую сессию
  (`token`) и публичные параметры показа (`zoneId`, `sdkUrl`), клиент подключает SDK
  (тег с `data-zone`/`data-sdk` создаёт глобальную `show_<зона>`) и зовёт
  `show_<зона>({ type: 'end', ymid: token, catchIfNoFeed: true })`; награда — только
  если сеть ответила `reward_event_type: 'valued'`. Пауза начинается с награды,
  поэтому неудачный показ не запирает кнопку. Chanify — запасная сеть: реклама
  приходит сообщением от бота в чат, показ проверить нельзя, поэтому энергию
  начисляем по возвращении игрока (`confirm`).
  Выдачи хранит таблица `ad_rewards`: `provider` различает сети, `external_id` —
  идентификатор показа на стороне сети, `postback_at`/`postback_value` — отметку о
  серверном постбеке (его `ymid` — это наш `token`), а путь `pending → credited`
  выполняет один запрос, поэтому награда не удвоится. Дневного лимита нет, пауза
  между попытками общая для всех сетей.
  Постбеки Monetag принимает `GET /api/ads/monetag/<секрет>` (секрет —
  `MONETAG_POSTBACK_SECRET`): адрес с ним вставляется в кабинете в поле Postback URL
  главной зоны SDK. По умолчанию постбек только отмечает показ, а энергию начисляет
  клиентский `claim`; с `MONETAG_REQUIRE_POSTBACK=1` награду выдаёт сам постбек
  (клиент ждёт подтверждения) — это защита от подделки показа с клиента. Окно ожидания
  считается от подтверждения клиентом (`client_done_at`, ставится первым `claim`):
  если постбек не пришёл за `MONETAG_POSTBACK_GRACE_MS`, награда всё равно выдаётся со
  `fallback: "grace"`, но без отметки постбека (`postback_at = 0`) — такие выдачи видно
  отдельным запросом, а `MONETAG_POSTBACK_GRACE_MS=0` отключает страховку совсем.
  Пассивный In-App Interstitial включается строкой `MONETAG_INAPP_SETTINGS`
  («частота/окно/интервал/задержка/сброс», например `2/0.1/30/5/0`): формат
  показывается сам, награды не даёт и постбеков не шлёт.
  Monetag включается, когда в `wrangler.toml` появятся `MONETAG_ZONE` и
  `MONETAG_SDK_URL` (публичные значения из кабинета); ключ `CHANIFY_API_KEY` лежит
  секретом воркера (его ставит `tools/cf-deploy.ps1`), `AD_MODE=stub` в `.dev.vars` и
  в staging означает «показ считаем успешным, сеть не дёргаем» — именно так работают
  автотесты, чтобы не рассылать настоящую рекламу.
- **Удаление профиля делает сам игрок** (`POST /api/profile/delete`): запрос не принимает
  идентификатор, поэтому удалить чужой профиль нельзя. Все записи игрока (карточки, задания,
  достижения, косметика, бусты, напоминания) и сессии удаляются одним `db.batch` — это
  транзакция D1, строк-сирот не остаётся. Платежи за звёзды сохраняются: по `user_id` и
  `charge_id` поддержка находит чек для возврата через `/paysupport`.
- **Рейтинг — по текущему балансу монет.** Индекс по `coins` намеренно не создаём: монеты
  меняются на каждой пачке тапов, и индекс удвоил бы расход записей D1 (а бесплатный тариф
  как раз ограничен записями). Снимок рейтинга считается одним проходом раз в 2 минуты
  и кэшируется на edge — этого достаточно при любом разумном числе игроков.
- **Уведомления не спамят**: одинаковый текст сворачивается в счётчик, у частых ошибок есть
  кулдаун, одновременно не больше трёх сообщений, живут внизу над таб-баром.
- **Бэкапы**: `wrangler d1 export` + встроенный Time Travel на 30 дней.

## Если что-то пошло не так

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `fetch failed` при импорте схемы или деплое | канал (VPN) рвёт одиночный запрос к Cloudflare API | запустить скрипт снова; схема применяется по утверждениям с повторами (`tools/cf-d1-apply.js`) |
| Локально не приходят напоминания | `wrangler dev` не запускает cron-триггеры автоматически | прогнать вручную: `curl "http://127.0.0.1:8787/cdn-cgi/local/scheduled"`; доставку проверить через `node tools/push-test.js` |
| `tools/star-sim.js` | проверяет путь оплаты без реальных звёзд: синтетические `pre_checkout_query` и `successful_payment`, выдача товара, запись чека и защита от повторов |
| `tools/star-refund.js` | `--list` — последние покупки с чеками; `<charge_id>` — возврат звёзд покупателю (`refundStarPayment`) |
| `code: 10034` / «You need to verify your email address» | у аккаунта Cloudflare не подтверждён e-mail | открыть письмо «Verify your email address» (проверьте «Спам») или dash.cloudflare.com → «Resend»; затем запустить скрипт снова |
| `Multiple environments are defined ... no target environment` | в `wrangler.toml` есть секция `[env.staging]` | это предупреждение, не ошибка: команда всё равно идёт в прод (верхний уровень конфига) |
| `code: 10007 This Worker does not exist` | воркер ещё не деплоился | нормально до первого `deploy` |
| Локально `tools/cf-check.js` ругается «после ролика энергия восстановлена» и «повторный claim не начисляет дважды» | в `wrangler.toml` включён строгий режим `MONETAG_REQUIRE_POSTBACK=1`, а награда локально приходит только после постбека сети (проверки в dev-части написаны для нестрогого режима) | это не про ваш код: тот же путь проходит в `tools/smoke.js` и в `tools/prod-check.js`; сам постбек проверяется строкой «постбек сети принимается» |
| В логе «`схему применить не удалось`» | сеть отвалилась на середине | запустить `node tools/cf-d1-apply.js hamster-tap` — инструмент идемпотентен (`IF NOT EXISTS`) и доделает остаток |
| Кнопка «🐹 Играть» не видна в чате | кнопка «по умолчанию» не всегда показывается там, где бот уже открывали | `node tools/bot-state.js` покажет текущее значение; `set-webhook.js` (и `cf-deploy.ps1`) ставят кнопку ещё и адресно для чатов; для нового чата достаточно отправить боту `/start` |

Инструменты и их назначение:

| Инструмент | Что делает |
| --- | --- |
| `tools/cf-deploy.ps1` | весь деплой по шагам (идемпотентно, с повторами на сетевых шагах) |
| `tools/ensure-subdomain.js` | проверяет и при необходимости создаёт workers.dev-поддомен аккаунта |
| `tools/cf-d1-apply.js` | применяет `cloudflare/schema.sql` по утверждениям; `--check` — только проверка таблиц, `--local`/`--env` — выбор базы |
| `tools/set-webhook.js` | webhook + команды + кнопка меню, в том числе адресно для чатов; `--dry-run` — показать план, не меняя состояние |
| `tools/push-test.js` | отправляет такое же напоминание, как рассылка (с кнопкой отписки): `node tools/push-test.js <chat_id> [energy\|daily\|rank]` |
| `tools/cf-check.js` | проверки API по боевому адресу (health, статика, 401/404, чужой секрет webhook) и, где разрешён dev-вход, полный игровой путь: тапы, бонус дня, покупка, задания, косметика, профиль, рефералка по настоящей ссылке `?startapp=ref_<tg_id>` с выплатой награды после 100 тапов друга, энергия за рекламу (сессия ролика Monetag, недосмотр без награды, награда и пауза, приём постбека сети по секретному адресу, запасной путь через рекламу в чате), оплата (двувалютная витрина, `/api/pay/info` без токена → 401, чужой секрет уведомления ЮKassa → 404), удаление профиля с проверкой, что сессия перестала работать |
| `tools/prod-check.js` | сквозная проверка прода по-настоящему: подписывает `initData`, проходит тапы, античит, буст, бонус дня, покупку, задания, косметику, профиль, настройки рекламы (включённая зона Monetag, настройки In-App, сессия ролика в строгом режиме и выдача награды по страховке), двувалютную витрину и список каналов оплаты, удаляет тестовый профиль через `POST /api/profile/delete` (как это делает игрок в интерфейсе), проверяет отсутствие строк-сирот в D1; с флагом `--local` работает против `wrangler dev` |
| `tools/bot-state.js` | состояние бота: токен, webhook, команды, куда ведёт кнопка меню (только чтение) |

## Проверка боевого окружения

```powershell
node tools/cf-check.js https://hamster-tap.<аккаунт>.workers.dev     # 78 проверок API (в проде — 8 публичных)
node tools/prod-check.js https://hamster-tap.<аккаунт>.workers.dev   # 65 сквозных проверок
node tools/bot-state.js                                              # webhook, команды, кнопка меню
```

`cf-check` работает и без Telegram, а `prod-check` собирает `initData` с настоящей подписью
(по алгоритму из `lib/auth.js`, ключ — `BOT_TOKEN` из `.env`) и проходит путь игрока на живом
окружении: вход → тапы → античит → бонус дня → турбо → покупка карточки → чтение из D1.
Тестовый игрок `777000123` удаляется из облачной базы в конце запуска.
